# Release performance audit: CPU, host and frame pacing

Audit date: 2026-11-02. Source snapshot: `74668b5c5b95651eb4b831938c0217a8ada6160e`, branch `codex-perf-cpu`.
Read-only inspection plus this document. No build, CMake, CTest, DXC, game launch, queue submission, Git mutation or commit.

## Decision

Prioritize reducing capture/provider lock contention, repeated binding lookups and query command recording. Preserve the current-frame scene and all Ultra effects. Then optimize submit-time mapped reads and BVH metadata construction. Moving the wait to the GPU requires architectural work; deleting the wait would regress moving shadows.

The camp's roughly 6.4 ms wait is real wall time on a lighting recording worker, but is neither 6.4 ms of GPU work nor a demonstrated 6.4 ms addition to presentation latency. The game records concurrently. Its final submit already requires the producer command buffer. The audit finds plausible sub-millisecond CPU increments; it does not establish an additive multi-millisecond release speedup.

## Where the layer adds work and latency

### Scene wait and overlapping the game's frame

The lighting worker asks `rt_scene_set` for the TLAS and alpha set. Only its first request per frame waits (`layer/rtscene.cpp:1380`). Another game recording thread finishes capture, records conversion/BVH work, commits the slot and makes its handles available. The condition variable releases `g_mu` while waiting (`layer/rtscene.cpp:1349`). It waits for CPU publication, not GPU completion. The log's mean divides by waited calls, not all calls (`:1368`); E1 happens to wait every frame.

The cause is explicitly documented at `layer/rtscene.cpp:153`: lighting recording starts before the G-buffer producer finishes. Their command buffers enter the same submit, producer first. Current-frame handles are selected during recording, so an ordinary semaphore cannot replace the CPU rendezvous. Disabling `rt_scene_wait` traces the previous camera-relative scene; the earlier primary match was 33% versus 97% with waiting (`docs/TRACK_D_SCENE_BUILD.md:806`). Lowering the 12 ms cap merely creates stale-scene timeouts. Keep `rt_scene_wait=1` in every RT preset.

Useful overlap has two levels. First, shorten the producer path and run immutable CPU preparation outside its locks, while preserving command-buffer ownership. Second, reserve a frame-specific scene slot/TLAS/descriptors before lighting recording, then finalize its contents before submission, with explicit lifetime and publication rules. The latter could remove some or all of the observed 6.4 ms worker wait, but the producer and GPU build still have to finish. It may save zero presented-frame time. A proxy TLAS or update-after-bind design is already identified at `docs/TRACK_D_SCENE_BUILD.md:809`; it is not a small semaphore change. Never record concurrently into the same game command buffer. Reusing last frame's data is not an Ultra solution.

### Scene build CPU versus GPU

CPU costs include draw classification, mesh-key maps, dynamic BLAS decisions, instance list construction and Vulkan command recording. The timer named “GPU convert/extract/compaction” in the CPU line measures CPU recording time (`layer/bvhsplit.cpp:2115`), whereas `[rt] scene build GPU` timestamps measure actual execution (`layer/rtscene.cpp:1544`). E6's 0.040 ms is not E8's 1.382 ms conversion execution.

Static meshes are already cached; TLAS refit and dynamic per-draw refit already exist (`docs/TRACK_D_SCENE_BUILD.md:593`, `:602`, `:608`). Dynamic eligibility checks include triangle count, flags, submitted source and rebuild interval (`layer/bvhsplit.cpp:1440`). Full rebuilds require a new address while old scenes are in flight (`:1443`). The default recording path already batches AS builds into one call (`:1927`); adding that same batching again has no benefit. Do not extend rebuild intervals or skip skinned/wind updates as an assumed quality-neutral optimization.

Remaining host targets are local scratch vectors/maps recreated in `bvh_build` (`layer/bvhsplit.cpp:1272`, `:1515`, `:1837`) and repeated invariant classification. E6/E7 bound the relevant CPU portions at roughly 0.5-1.5 ms/build, with substantial workload dependence. Worker preparation should handle immutable descriptors/keys, not live mapped instance values or command-buffer emission.

### Geometry capture, hook overhead and descriptor work

Every intercepted draw looks up command state, then captured draws execute pre/driver/post hooks (`layer/cmd.cpp:675`, `:685`). `cmd_state` takes a shared lock and hashes the handle (`:55`); binding queries can repeat this lookup. XFB capture changes bindings and reserves ranges per draw (`layer/geocapture.cpp:2331`, `:2431`). E5 exposes large historical pre-draw cost, but its 16.954 ms total is not the current release overhead. E3 is a better indication of residual provider work with the automatic keys enabled.

Capture already has a cached static-mesh path and lean candidate filtering. Cache pipeline eligibility and immutable binding metadata with generation invalidation; pass the resolved state through internal helpers. Keep mutable offsets, camera epochs, descriptor content and resource lifetimes current. A persistent pointer cache without command-buffer reset/free invalidation would be unsafe (`layer/cmd.cpp:72`).

The watchdog counts intercepted game-facing writes/copies (`layer/tracker.cpp:767`, `:772`, `:817`), not descriptor elements or all layer work. Internal calls such as `dd->vk.UpdateDescriptorSets` in `layer/hit_material.cpp:1359` bypass this counter; push descriptors also differ from host descriptor updates. Thus E9 does not prove that the layer writes only 4 descriptors/frame, nor that descriptor writes dominate CPU time. Tracker writes currently update bookkeeping per write; batching that bookkeeping under one appropriate lock is more plausible than delaying the game's Vulkan updates. Internally, alpha clones use several update calls (`layer/alphatest.cpp:1447`, `:1617`, `:1637`). Coalesce compatible writes/copies before first use, retaining slot ownership. Do not alter game command order.

### Hit-material packets and query recording

Prepass hooks append under `pending_mutex`, still shared across recordings; scene preparation takes provider and pending locks (`layer/hit_material.cpp:99`, `:712`, `:732`). E3 retains 0.624-0.686 ms/frame of aggregate mutex wait. Move candidate accumulation to recording-owned storage and publish once; snapshot immutable material metadata under a short lock. That can reduce serialization without changing captured geometry.

The query still holds the provider mutex across pairing, table assembly, allocation and GPU command recording (`layer/hit_material.cpp:1095`). It already reuses a query within the same recording and generation (`:1104`). Its outer scene-lock pin/release is already implemented (`layer/rtscene.cpp:1429`); do not claim that as new work. Each row emits `CmdUpdateBuffer`, push constants and a join dispatch (`layer/hit_material.cpp:1366`, `:1372`). Group row uploads and represent join jobs in a compact work list; preserve exact GPU clip/UV comparison, row publication and instance remap. Group by chunk where valid; the current join already suppresses redundant descriptor pushes until the chunk changes (`:1374`). E3's query 0.916-0.956 ms is an upper envelope for this opportunity, not all removable work.

### Copies, allocations and submits

Submit-time instance transforms must be read after the game has finished its mapped writes (`layer/bvhsplit.cpp:2327`, `:2348`). SIMD streaming loads already replaced expensive ordinary reads of write-combined memory (`:63`). E7's 0.507-0.603 ms for about 633 matrices is the current opportunity; the old 28 ms comment is not a remaining saving. Deduplicate identical source ranges within one submit, load once, validate once and scatter to every destination. Never cache those values across frames or move reads back to record time.

Hit-material source copies must precede the in-place soup conversion (`layer/hit_material.cpp:762`; `docs/TRACK_D_SCENE_BUILD.md:842`). They cannot simply be deleted. Batch compatible copy regions and row uploads; avoid an extra CPU staging copy where direct mapped construction is valid. E10 caps water/FG copy savings near 0.050 ms GPU combined for that scene even if both could disappear; their ownership and transitions still matter. This is lower priority than CPU serialization.

The submit wrapper constructs a command list each call and walks several consumers (`layer/layer.cpp:458`, `:467`, `:474`). The watchdog counts wrapper entries, not every internal driver submission (`:457`), so E9's 4/frame is not four removable layer submits. Reuse scratch capacity and bypass consumers known to have no pending work. Coalesce only layer-owned auxiliary work with compatible semaphores, fences and ordering; never fuse the game's submits arbitrarily. Actual completion governs retirement, including OMM (`docs/P4_OMM.md:36`), not a fixed number of presents.

GPU-buffer recycling, size fitting, per-frame collection throttling and deferred frees are already present (`layer/hit_material.cpp:319`, `:347`, `:508`, `:701`). Preserve automatic `rt_hit_material_recycle`, `_capture_unlocked`, `_lean_hooks` (`common/settings.h:438`, `:585`). E5's 5.299 ms allocation/free cost is largely historical. E3's residual allocation/free subtotal is 0.029-0.094 ms; claiming another 5 ms from pooling would double-count the shipped fix. CPU scratch reuse can help jitter but is not independently timed in these logs.

### Shader/pipeline hitches and FG pacing

Runtime SPIR-V disk caching and background request prefetch already exist, but first-use requests can compile or wait for an in-progress entry (`layer/shaders.cpp:335`, `:427`, `:444`). The historical 3.1-3.4 s per cold compile and absence of an explicit VkPipelineCache are documented in `docs/BUILD_AND_PACKAGE_EFFICIENCY.md:15`, `:22`. Those are event costs, not milliseconds every frame. Source snapshot still calls scene pipeline preparation from present (`layer/rtscene.cpp:1507`).

Native hair's asynchronous compile work is pending on its branch (`docs/HANDOFF_SESSION.md:35`; `docs/PROGRESS_CODEX.md:16`). Treat it as existing parallel work, not a new performance project or a verified property of this snapshot. Integrate and verify that path first. Then prewarm the actual release/Ultra shader and pipeline set before interactive gameplay, including new specialization combinations; do not use the older document's “100 plain entries” as an exact current Ultra inventory. Specialization migration reduces DXC requests but can still create driver pipelines. Persistent VkPipelineCache is secondary to measured cold misses and the driver's existing cache (`docs/BUILD_AND_PACKAGE_EFFICIENCY.md:173`). E12's 67 ms is interval-summed intercepted driver time, not a single 67 ms hitch and not all internal pipeline creation.

`[pace]` measures intervals between the game's presents before FG (`layer/layer.cpp:716`), including scheduling, caps and any upstream stalls. It is not input-to-photon latency. FG displayed counts cannot replace rendered-frame pacing. Reflex sleep is intentional (`layer/streamline.cpp:967`); removing it to inflate throughput can increase latency. Preserve frame tokens, markers, input copies and completion-fence handling (`docs/TRACK_B_FG.md:343`).

The literal `Frame rate over 100 ms` warning was not found in the inspected 154 queue logs or current `bg3rtx.log`. Historical evidence is documented at `common/vram_guard.h:7`: process VRAM crossed the budget while BLAS reservations and cascade capture grew. E11 independently shows severe current frame/build tails, but does not prove their cause. Correlate `[mem]`, scene GPU tails, cache events, load transitions and FG state before blaming Reflex. Reclaim completed unused allocations and avoid unnecessary growth/fragmentation; never reduce Ultra geometry coverage or deny required allocations and call it quality-preserving. `rt_vram_guard` remains experimental (`common/settings.h:357`).

## Future A/B measurement contract (not executed or queued)

The job names above are proposed jobs, not existing validated queue artifacts. Base their scene plans on the existing `sw3` pan/rotation and `smoke_ultra` patterns. One change per A/B; all qualified Ultra keys stay on. Use S3 camp for foliage/capture pressure, S8 Water Queens House for motion/submit/copies, and S6 foundry for emissive materials. Confirm each candidate in `smoke_ultra` after its isolated result.

1. Within one authorized session per save, alternate baseline/candidate/baseline/candidate on the same repeatable static and pan/rotation phases. Keep the game unfocused with `window_mode: visible_unfocused_fg` when the user is at the PC; capped pacing cannot prove throughput. No builds or compiles during cost windows.
2. Use proposed switches to toggle host behavior within the run. CPU attribution windows require the diagnostics layer and `cpu_timing=1`; normal release compiles those capture timers out (`layer/cmd.cpp:40`; `docs/ARCHITECTURE.md:41`). Use >=300 steady frames per CPU sample and >=600 per pacing sample, accounting for cadence boundaries. A few 120-frame windows alone cannot produce a 600-frame pacing comparison. Separate expensive primary/RT stats from clean cost windows.
3. Include job `patterns`, `expect`, and `expect_every` for every ON cost window. Require zero scene-wait timeouts/skips during gameplay, current-frame TLAS for every RT pass, zero capture/stream/basis/mesh capacity drops and unchanged material coverage. Keep `rt_scene_wait_log_frames=120`, with adequate holds for each expected line. Cross-window averages cannot hide a bad ON window (`scripts/queue_gates.py:312`).
4. Decide CPU savings from the relevant E3/E6/E7 timer, not watchdog counts or reduced GPU quality. Record scene-build GPU and GI/LS/RF/water cost lines in both states. Derive tolerances from key-off repeat noise; do not assert a universal 0.1 ms gate. If the confidence interval includes zero, retain no positive saving claim.
5. Use a short separate primary-reference/coverage capture to verify camera motion and same-frame identity; static pre-post scene float mean from `dumps.json` must stay within key-off repeat noise. Do not use PNG or bloom brightness. No lower energy, omitted materials, stale transforms or skipped startup effects count as performance wins.
6. For cold/warm tests, name cache state and correlate cache waits with toggle gaps and pacing tails. For the long-view memory case, correlate `[mem]` budget/headroom and scene-build GPU p99 with actual warning timestamps and FG state. Keep intentional loading/compilation windows separate from steady-state results. `[pace]` plus displayed/rendered ratio does not measure end-to-end latency; that remains unmeasured here.
